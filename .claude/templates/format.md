# Spec Format Contract

Shared conventions for all `ba` skills. Every skill that reads or writes `specs/` follows this file. **Human-readable markdown + machine-parseable structure. Versioning is git — no changelogs, no revision tables, no version numbers inside files.**

## Layout (one layout for every project, any size)

```
specs/
├── overview.md               # thin index: scope, roles, module map — loaded first by every skill
├── glossary.md               # domain terms
├── rules.md                  # cross-cutting rules ONLY (CBR-*)
├── edge-cases.md             # global edge cases ONLY (EC-GLOBAL-*)
├── decisions.md              # global decisions (D-GLOBAL-*) — same shape as module decisions.md
├── registry/                 # living SSOT layer — seeded at scope-gate, appended as modules land
│   ├── entities.md           # entity → exactly one owner + shared-entity contracts
│   ├── catalogs.md           # shared enums/catalogs (CAT-*) + shared constants (CONST-*)
│   ├── rbac.md               # role taxonomy + permission matrix (roles × modules × actions)
│   └── messages.md           # message-prefix registry (one prefix ↔ one module)
├── modules/<slug>/           # one folder per module — an agent working a module opens ONLY this folder (+ the 3 globals)
│   ├── index.md              # entry point: frontmatter status + purpose, actors, entities, open items
│   ├── requirements.md       # user stories + EARS acceptance criteria + Mermaid flows
│   ├── data.md               # entities, fields, validation, state machines
│   ├── rules.md              # module business rules (BR-<MOD>-*) — each rule defined here ONCE
│   ├── edge-cases.md         # EC-<MOD>-*
│   ├── decisions.md          # append-only: what the client decided + why (ADR-lite)
│   └── test-cases.md         # TC-<MOD>-* — GENERATED by the testcase-generator agent from the other files; regenerated on spec change, never hand-edited
└── .clarity/                 # working caches only — NEVER spec content
    ├── discussion-log.md     # from the discuss mode
    ├── domain-research.md    # ba-domain-researcher cache
    └── intake/<slug>.md      # raw client input quoted per module (written at scope-lock)
```

## Frontmatter (the machine index — enables cheap status scans)

`modules/<slug>/index.md` MUST start with:

```yaml
---
id: <slug>
status: pending | clarifying | documented
priority: P0 | P1 | P2
depends_on: [<slug>, ...]
---
```

`overview.md` starts with `--- \n project: <name> \n domain: <one-line> \n ---`.

Status scans read ONLY frontmatter (first ~10 lines of each `index.md`) — never file bodies. There is no `state.json`; frontmatter is the single source of module status.

## Clarification markers (single source for open questions)

An unresolved point lives **inline, at the exact spot in the file where the gap is** — never in a separate question list:

```
[NEEDS-CLARIFICATION: Q-<MOD>-NN (high|medium|low) — <question>? — suggested: <default>]
```

- Before a module's spec exists, markers live in `.clarity/intake/<slug>.md` (an `## Open questions` section is fine there).
- When the spec is generated, unresolved markers move into the spec file at the relevant location.
- Resolving a question = edit the spec text at the marker + append an entry to `decisions.md` + delete the marker.
- All status/export/refine tooling finds open questions by grepping `NEEDS-CLARIFICATION` across `specs/` — nothing else tracks them.

## IDs — stable, scoped, hyphenated (never underscores)

| Prefix | Meaning | Defined in (one place only) |
|---|---|---|
| `REQ-<MOD>-NN` | requirement / user story | `requirements.md` |
| `BR-<MOD>-NN` | module business rule | module `rules.md` |
| `CBR-NN` | cross-cutting rule | global `rules.md` |
| `EC-<MOD>-NN` / `EC-GLOBAL-NN` | edge case | module / global `edge-cases.md` |
| `VAL-<MOD>-NN` | validation constraint | `data.md` |
| `D-<MOD>-NN` / `D-GLOBAL-NN` | decision | module / global `decisions.md` |
| `Q-<MOD>-NN` / `Q-GLOBAL-NN` | open question | inline marker (see above) |
| `Q-REG-NN` | open question about a registry-level (cross-module SSOT) item | inline marker in `registry/*` |
| `D-REG-NN` | registry-level decision (cross-module SSOT) | global `decisions.md` |
| `TC-<MOD>-NN` | test case (generated) | `test-cases.md` |

IDs are anchors, not just labels — see the OKF section below for how a heading turns into something another file can point at.

## OKF profile (Open Knowledge Format — every spec file is a graph node)

Every `.md` file under `specs/` is a node in one project-wide graph. A node's frontmatter declares what it *is* (`type`) and how it *relates* to other nodes (`relations`); its body may additionally link to other nodes inline. There is no bare-ID reference left anywhere — an ID either anchors a heading in the file that owns it, or it is the target of a `relations` edge / markdown link in the file that points at it.

**(a) Frontmatter carries `type` + `relations`.** `type` names the kind of node (`module`, `entity-index`, `catalog`, `role`, `message-prefix`, …). `relations` is a YAML list of typed edges, each `{type: <edge>, target: "<file>#<ID>", note: "<optional one-liner>"}` (same-file target: `target: "#<ID>"`). The edge vocabulary is closed — no other edge type is valid:

`owns` · `consumes` · `produces` · `triggers` · `gated-by` · `depends-on` · `references` · `defined-by`

```yaml
---
id: m01
type: module
status: documented
priority: P0
depends_on: []
relations:
  - {type: owns, target: "#Invoice"}
  - {type: consumes, target: "../m02/data.md#Client", note: "reads billing address"}
  - {type: gated-by, target: "../../registry/rbac.md#ROLE-FINANCE"}
---
```

**(b) Anchor rule.** `#<ID>` resolves against a target file if any of the following is true:
1. the file has a heading whose first token is exactly `<ID>` — e.g. `### REQ-M02-01: Create ticket` anchors `REQ-M02-01`;
2. the heading carries an explicit `{#<ID>}` (use this when the natural heading text isn't the bare ID);
3. the file's own frontmatter `id:` equals `<ID>` (whole-file target, e.g. linking to a module by its slug).

**(c) Prose "reference by ID" MUST be a markdown link.** Naming an ID in running text is never a bare token — it is always `[ID](file#ID)` (or `[ID](#ID)` same-file). A reader — human or agent — must be able to click/resolve every ID mentioned in prose.

**(d) `relations` is canonical; inline links must also resolve.** Structural facts (this module owns this entity, this rule gates this action, this module consumes that catalog) live in `relations` — that is what `check_graph.py` and the generated views read. Inline markdown links in the body are for readability and MUST resolve to the same graph (same file + anchor rule) — they are not a separate, unchecked reference channel.

**(e) Shared values are still defined once.** The registry discipline is unchanged in substance: an entity/catalog/constant/role/message-prefix shared by 2+ modules is defined once in `registry/`, as a heading-anchored ID. A module never copies those values — it adds a `consumes` (or `gated-by`/`references`, as fits) relation targeting the registry heading, plus an inline link at first mention in prose. Copying a catalog's values, a role's permissions, a shared constant, or a shared entity's fields into a module file is forbidden — duplicated text drifts, that is the conflict source.

**(f) Ownership map + prefix map are GENERATED — never hand-edit.** `scripts/gen_views.py` derives the entity-ownership map and the message-prefix map from every node's `relations` and writes them to `registry/_views/` (`registry/_views/ownership-map.md`, `registry/_views/prefixes.md`). Those files are build output: if reality and a hand-edit disagree, the hand-edit is wrong. To change ownership, change the `owns` relation at the source and regenerate.

**(g) The validator must pass before `documented`.** `skills/spec/scripts/check_graph.py` walks the graph and reports:

| Code | Meaning |
|------|---------|
| `UNRESOLVED` | a `relations` edge or inline link points at a file/anchor that doesn't exist |
| `OWN_DUP` | two-plus modules declare `owns` on the same anchor |
| `OWN_ORPHAN` | something is `consumes`d/`produces`d/etc. but nothing `owns` it |
| `MSG_LEAK` | a message code uses another module's owned `MSG_<MOD>_` prefix |
| `ID_DUP` | the same ID heading is defined twice |
| `EDGE_VOCAB` | a relation uses an edge type outside the closed vocabulary above |

A module's `index.md` frontmatter `status` may not move to `documented` while `check_graph.py` reports any finding rooted in that module's files.

Module numbers/slugs are fixed at the scope-gate: `overview.md`'s module map is the SSOT for module identity — never renumber a module once assigned.

## Writing rules

- **EARS notation** for acceptance criteria: `WHEN <trigger>, THE SYSTEM SHALL <behavior>` / `WHILE <state>...` / `IF <condition>, THEN THE SYSTEM SHALL...` / `THE SYSTEM SHALL...`
- **Mermaid** for every diagram (never ASCII art). Flow steps as numbered markdown lists (never `<br>`-joined table cells).
- **Fixed headings**: use the exact heading names from the templates in every module — agents parse by heading.
- **Tables over prose** for enumerable facts; prose only for rationale.
- **No generated-date/score/version headers.** Git blame answers "when"; markers answer "what's unclear".
- Sections with nothing to say: `n/a` + one line why (never delete the heading).
- All spec output in English.
